02 · Columns and transitions

A total projection, not a second workflow engine.

Every input object lands exactly once. The source of truth stays in Beads and the Go-computed PR gate array; Refresh simply reruns the projection.

ObjectSource stateColumnMeaning shown to the user
Workstreamopen, deferred, unknown nonterminalPlannedNot actively executing. Raw status remains visible; unknown is never hidden.
Workstreamin_progress without explicit track:testActiveImplementation or other execution is underway.
Workstreamin_progress plus the persisted Beads label track:testVerifyingAn explicitly identified verification track is executing. Titles and session names are never guessed.
WorkstreamblockedBlockedCannot proceed; the reason/state is textual as well as colored.
WorkstreamclosedDoneCompleted work, with child progress when a hierarchy exists.
Pull requestOpen initiative; gate emptyActiveThe PR exists and is not explicitly waiting on anyone. The badge says “open · no explicit gate”; it does not claim implementation, checks, or testing state.
Pull requestOpen initiative; gate reviewYour ReviewThe persisted gate:review signal explicitly asks you to review this PR.
Pull requestOpen initiative; gate externalExternal ReviewThe human has declared their review complete via handoff; this PR is with other reviewers.
Pull requestOpen initiative; gate questionBlockedA specific PR is waiting on a decision.
Pull requestInitiative closed or doneDoneInitiative completion wins. The first loop does not claim a per-PR GitHub merge fact.
03 · Card and data model

Two card types; one honest board.

W

Workstream card

Derived from root-epic children in workBeads. Shows bead id, title, raw status, type, priority, and recursive child progress. Bare or orphan legacy work remains visible.

PR

Pull-request card

Derived from ordered prs, joined to prReviews by exact URL. Shows a compact repo/number label, safe external link, and explicit per-PR gate.

∅

No invented relationship

The current payload has no durable PR-to-workstream key. Cards therefore remain siblings. Position, title, repo, or branch will never be used as a hidden association heuristic.

Card anatomy

  • Eyebrow: object kind + priority or destination
  • Title: human-scannable work or repo#PR
  • Identity: stable bead id or canonical PR URL
  • State chips: raw and explicit, never color-only
  • Progress: descendant closed/total for hierarchical work

Transition safeguards

  • Done precedence before all other placement
  • Blocked/question precedence before every other nonterminal placement
  • Verifying requires both in_progress and exact label track:test
  • An empty PR gate falls back to Active with an explicit unknown-state badge
  • Unknown work status gracefully falls back to Planned
  • No duplicate/drop: every input is accounted for
  • Stable source ordering prevents refresh jitter
04 · What the repository already provides

The smallest loop is frontend-only.

Shared response is already rich enough.dashboard/shared/types.ts defines WorkBead, PRReview, and DrillInDetail with ordered PRs and work beads.
The detail endpoint already joins the sources.dashboard/server/src/index.ts GET /api/initiatives/:id returns snapshot initiative data, matched sessions, labeled Beads, and notes history.
PR gate state is computed upstream.ateam list-json emits prs and aligned pr_reviews. review is an explicit review ask; external is an explicit completed-human-handoff declaration; empty means no explicit gate.
Verification is explicit in Beads.bd list --label … --status=all --json carries both status and exact labels into workBeads. Only in_progress + track:test means Verifying; other work never gets classified from title or session-name prose.
The current frontend seam is concentrated.dashboard/web/src/views/drillin/index.tsx, drillin.css, and drillin.test.tsx own the current route’s view, style, and regression surface.
No new write contract is justified.The current server route is read-only. Drag/drop would require product semantics and mutation APIs that do not exist and are not needed to close the visual loop.

06 · Testability

The build is testable at four levels.

Pure model witnessesEvery status/gate mapping, precedence, root exclusion, legacy hierarchy fallback, multi-PR disagreement, stable ordering, and total accounting.
React behavior witnessesSeven columns and counts, card anatomy, safe PR links, noninteractive cards, Refresh success/failure, and preserved Back/Attach/log/session/note behavior.
Repository gatesBuild shared first, then targeted Vitest, web typecheck/build, full server tests, and full web tests. Partial test collection does not count.
Live observable verificationReal multi-PR and multi-child initiatives; 1440/1024/390px; horizontal board vs stacked board; keyboard focus; reduced motion; explicit Refresh; preserved operational details.
07 · Accessibility and responsive behavior

Wide when comparison matters; stacked when reading matters.

≥

Wide viewport

Seven fixed/min-width columns in one visibly bounded horizontal region. The board scrolls; the page does not. Column comparison stays intact.

≤

Narrow viewport

Columns stack Planned→Active→Verifying→Your Review→External Review→Blocked→Done. Long titles and URLs wrap, with no document horizontal overflow.

A11y

Semantic and keyboard-safe

Native sections/headings/lists/links, announced names and counts, visible focus, written state labels, no fake card buttons, and reduced-motion support.

  • Test fixture details and representative real initiative used live
