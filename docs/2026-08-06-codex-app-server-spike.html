Codex app-server lifecycle

What survives when the client, launcher, or native Codex server dies—and what that means for mail wake-up.

GO for app-server Codex 0.145.0 + 0.146.1 2026-08-06 PR #160
Decision: require standalone Codex and use its managed app-server daemon. Codex owns the durable daemon; ateam owns short-lived, locked mail delivery and crash reconciliation. Remove detached per-turn codex exec workers from the design.

The protocol baseline comes from OpenAI's Codex app-server reference. The results below are live observations, not behavior inferred from the documentation.

There is no long-lived ateam supervisor in this design. Each delivery attempt idempotently ensures the managed daemon is running, connects, and reconciles the target thread under a short-lived delivery lock. If that client disappears, the turn continues. If the daemon dies, the next attempt restarts it; the old turn becomes interrupted and the same thread accepts a recovery turn.

The supervisor question

The spike separated three processes:

  1. the JSON-RPC client, such as ateam;
  2. the CLI launcher process; and
  3. the native app-server process that owns threads and turns.

Killing launcher PID 3879 left native PID 3880 alive. A fresh client read the active turn and delivered MAIL_AFTER_LAUNCHER_DEATH_83b0ca. This directly answers the original concern: losing the supervising launcher is recoverable while Codex remains alive.

Killing native PID 3880 is different. The restarted server read the old turn as interrupted, resumed the same thread idle, and completed a new recovery turn. The managed-daemon follow-up reproduced this through the official lifecycle: PID 37709 detached under PID 1, graceful stop drained a turn, and hard-killing restarted PID 41280 was recoverable. What remains is a delivery coordinator, not an always-running supervisor.

What ateam must still own

  • A per-initiative delivery lock around state inspection and wake selection.
  • Beads messages and the doorbell as durable truth.
  • turn/steer(expectedTurnId=…) for active delivery.
  • thread/resume plus turn/start for idle or unloaded delivery.
  • Idempotent daemon start and post-crash reconciliation.
  • Doorbell clearing only after ateam mail inbox consumes unread mail.
Status caveat: during development, thread/read briefly synthesized a just-started turn as interrupted with no completion timestamp, although its rollout then recorded normal completion. Production code must not clear mail from status alone. Prefer turn/completed events and require durable completion metadata during reconnect polling.

Installation contract

codex app-server daemon start refused the npm/mise Codex 0.145.0 installation. Standalone Codex 0.146.1 exposed the fixed managed binary at ~/.codex/packages/standalone/current/codex and passed the full daemon lifecycle spike.

The first Codex slice therefore requires standalone Codex. Shared setup/audit logic must report Codex absent, Codex present in an incompatible layout, or compatible standalone Codex. General setup warns when optional Codex is incompatible; explicitly selecting the Codex runtime fails with an actionable installer message. The Claude setup skill and future Codex setup skill must invoke that same check.

PR #160 consequence

PR #160 now preserves runtime metadata, thread binding, Claude fallback, and adapter boundaries while replacing the Codex per-turn runtime-worker with the managed-daemon app-server client. The mail coordinator builds its delivery lock and durable reconciliation on that client rather than process ownership.

Remaining operational verification

The daemon deployment gate is settled. Logout/reboot and CLI-upgrade behavior remains a compatibility check, not a blocker for replacing the per-turn worker contract. Every delivery attempts an idempotent daemon start, so mail wake does not depend on login-time bootstrap.
