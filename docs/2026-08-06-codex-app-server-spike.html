Codex app-server lifecycle

What survives when the client, launcher, or native Codex server dies—and what that means for mail wake-up.

GO for app-server Codex 0.145.0 2026-08-06 PR #160
Decision: use app-server as the preferred Codex DRI runtime. Keep a small external daemon supervisor and an ateam-owned delivery lock; remove the detached codex exec process from the center of the design.

Markdown source · Reproduction harness · Runtime roadmap

The protocol baseline comes from OpenAI's Codex app-server reference. The results below are live observations, not behavior inferred from the documentation.

Result in one picture

The supervisor keeps or restarts the daemon. It does not own every model turn. If the client or launcher disappears while native app-server remains alive, another client reconnects to the same active turn. If native app-server dies, the old turn becomes interrupted and the same thread accepts a recovery turn after restart.

The supervisor question

The spike separated three processes:

  1. the JSON-RPC client, such as ateam;
  2. the CLI launcher process; and
  3. the native app-server process that owns threads and turns.

Killing launcher PID 3879 left native PID 3880 alive. A fresh client read the active turn and delivered MAIL_AFTER_LAUNCHER_DEATH_83b0ca. This directly answers the original concern: losing the supervising launcher is recoverable while Codex remains alive.

Killing native PID 3880 is different. The restarted server read the old turn as interrupted, resumed the same thread idle, and completed a new recovery turn. Therefore the external supervisor still matters—but only for daemon health and mail replay.

What ateam must still own

  • A per-initiative delivery lock around state inspection and wake selection.
  • Beads messages and the doorbell as durable truth.
  • turn/steer(expectedTurnId=…) for active delivery.
  • thread/resume plus turn/start for idle or unloaded delivery.
  • Daemon health, restart, and post-crash reconciliation.
  • Doorbell clearing only after ateam mail inbox consumes unread mail.
Status caveat: during development, thread/read briefly synthesized a just-started turn as interrupted with no completion timestamp, although its rollout then recorded normal completion. Production code must not clear mail from status alone. Prefer turn/completed events and require durable completion metadata during reconnect polling.

Installation constraint

codex app-server daemon start refused the npm/mise Codex installation on this machine. Codex 0.145.0 requires its standalone install at ~/.codex/packages/standalone/current/codex for managed-daemon commands. The spike did not alter the machine; it ran the same native app-server on a private loopback socket.

Before production implementation, decide whether agent-teams requires standalone Codex or owns a user-service fallback. Do not depend on npm wrapper orphaning as a supported supervision contract.

PR #160 consequence

Preserve runtime metadata, thread binding, Claude fallback, adapter boundaries, and fake-backed selection tests. Replace the Codex per-turn runtime-worker with an app-server client plus daemon manager. Amend the frozen runtime contract before starting the mail-wake implementation.
